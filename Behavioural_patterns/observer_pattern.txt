1️⃣ Problem First (Why Observer Pattern?)

Imagine this situation:

You have one object whose data changes (e.g., Weather, Stock Price, Order Status)

Many other objects need to react to that change (e.g., displays, alerts, logs)

❌ Naive Approach
class WeatherStation {
    void updateTemperature() {
        display1.update();
        display2.update();
        display3.update();
        // tightly coupled 😨
    }
}


Problems:

Hard-coded dependencies

Adding/removing listeners is painful

Violates Open–Closed Principle

👉 We need loose coupling

2️⃣ Observer Pattern – Core Idea (Plain English)

Observer Pattern defines a one-to-many dependency
so that when one object changes state,
all its dependents are notified automatically.

3️⃣ Real-Life Analogy 📢
YouTube Channel

Subject → YouTube Channel

Observers → Subscribers

New video uploaded → All subscribers get notified

Subscribers don’t poll the channel again and again.
The channel pushes updates.

4️⃣ Basic Structure (UML Thinking)
Roles

Subject

Maintains list of observers

Registers / removes observers

Notifies observers

Observer

Defines update() method

5️⃣ Step-by-Step Basic Implementation (Java)
Step 1: Observer Interface
interface Observer {
    void update(int temperature);
}

Step 2: Subject Interface
interface Subject {
    void registerObserver(Observer o);
    void removeObserver(Observer o);
    void notifyObservers();
}

Step 3: Concrete Subject
class WeatherStation implements Subject {
    private List<Observer> observers = new ArrayList<>();
    private int temperature;

    public void setTemperature(int temp) {
        this.temperature = temp;
        notifyObservers();
    }

    public void registerObserver(Observer o) {
        observers.add(o);
    }

    public void removeObserver(Observer o) {
        observers.remove(o);
    }

    public void notifyObservers() {
        for (Observer o : observers) {
            o.update(temperature);
        }
    }
}

Step 4: Concrete Observers
class PhoneDisplay implements Observer {
    public void update(int temperature) {
        System.out.println("Phone Display: " + temperature);
    }
}

class TVDisplay implements Observer {
    public void update(int temperature) {
        System.out.println("TV Display: " + temperature);
    }
}

Step 5: Client
public class Main {
    public static void main(String[] args) {
        WeatherStation ws = new WeatherStation();

        ws.registerObserver(new PhoneDisplay());
        ws.registerObserver(new TVDisplay());

        ws.setTemperature(30);
        ws.setTemperature(35);
    }
}


✔ Loose coupling
✔ Dynamic observers
✔ Clean design

6️⃣ Push vs Pull Model (Interview Favorite 🔥)
Push Model (Above)
update(int temperature)


Subject pushes data

Simple

Less flexible

Pull Model
interface Observer {
    void update();
}

class WeatherStation {
    int getTemperature() {
        return temperature;
    }
}


Observer pulls required data:

public void update() {
    int temp = weatherStation.getTemperature();
}


📝 Interview Tip

Pull model is more flexible but slightly more complex.

7️⃣ Java Built-in Observer (Why It’s Deprecated ⚠️)

Java had:

java.util.Observer
java.util.Observable


Why deprecated?

Class inheritance forced

Poor design choices

Not interface-based

👉 Modern Java uses custom observer or event-driven approaches

8️⃣ Advanced Level – Real Industry Patterns
🔹 Event-Driven Observer (Backend)

Example:

OrderPlacedEvent

PaymentService

EmailService

InventoryService

class OrderPlacedEvent {}

interface EventListener {
    void onEvent(OrderPlacedEvent event);
}


Each service reacts independently.

🔹 Observer + Multithreading (Important)

Problem:

One slow observer blocks others

Solution:

ExecutorService executor = Executors.newFixedThreadPool(4);

for (Observer o : observers) {
    executor.submit(() -> o.update(data));
}


✔ Async notifications
✔ High performance

9️⃣ Observer vs Pub-Sub (Very Important Difference)
Observer	Pub-Sub
Subject knows observers	Publisher doesn’t know subscribers
Tight relationship	Fully decoupled
In-process	Distributed (Kafka, RabbitMQ)

Observer ➜ Design Pattern
Pub-Sub ➜ Architecture Pattern

🔟 When to Use Observer Pattern ✅

Use when:

One object changes frequently

Multiple objects depend on it

You want loose coupling

Avoid when:

Order of notification matters heavily

Too many observers → performance issues
